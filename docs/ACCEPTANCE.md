# Acceptance trace and verification limits

Current production implementation and actual checks are in [the evidence record](production/05-evidence.md), [milestone board](production/reports/STATUS.md) and [release review](production/reports/M6-release-review.md). Durable identity/session/worker recovery, all panels, Google OAuth, strict granted in-app tools and local PostgreSQL restore are implemented with recorded local evidence. A real read-only Live contact lookup round trip passed after two separately preserved diagnostic failures; no telephone or Calendar effect occurred. Browser and synthetic-audio success do not establish signed-iPhone, human usability, real-service sandbox or complete accessibility acceptance. The original foundation matrix below retains those distinctions; old test counts are historical.

This record maps the original brief to concrete behavior and remaining gates. **Simulation is a working product demonstration, not evidence of a call, voice quality or an external agreement.** Run `npm test`, `npm run typecheck` and `npm run demo` from the root for current local evidence. Test totals alone do not establish acceptance; the consequential assertions below matter.

The provider adapter tests use injected, mocked HTTP. The domain tests use deterministic transcripts. Backend tests exercise persisted state, authentication and jobs locally. Expo’s web export can verify JavaScript packaging but cannot establish an iPhone binary, native permissions, VoiceOver usability or App Store readiness.

## Reproducible demonstrations

The seed data is fictional and uses reserved example numbers. Start with an isolated demo account. Run the appointment scenario and inspect the existing demo event’s ID/time before and after. Run information gathering and verify no booking action exists. Run the refund fixture and verify review is promised while the refund remains unresolved. Run `counteroffer` in delegated and assisted modes, `injection`, `refusal`, `wrong_person`, `voicemail`, `no_answer`, and `dropped_uncertain`; inspect transcript evidence and ensure no unauthorized follow-up exists. Run `calendar_failure` and retry the pending action without repeating the call.

Only the local simulator can run these scenarios without provider credentials. Before any real call, use the concrete plan in [PROVIDERS.md](PROVIDERS.md), configure exact processing/retention disclosure, obtain the recipient’s required consent and the owner’s explicit authorization for that test. Supplying credentials is not authorization to call.

## Release gates still open

- A macOS/Xcode or authorized EAS iOS build, signing and a real iPhone test.
- VoiceOver, large text, keyboard focus, contrast, permission-denied and reduced-motion checks on device.
- A consented allowlisted real-call pilot covering disclosure, refusal, end control, uncertain state and provider reconciliation.
- A validated bounded conversation flow before enabling live agreements, spending, bookings or external actions.
- Commercial multi-customer cloning rights, quota/account arrangement, provider verification and accessible fallback review.
- Per-user calendar OAuth onboarding, encrypted refresh/revocation handling and real calendar follow-through testing.
- Production authentication recovery/verification, operator abuse response, legal/privacy notices, retention policy and App Store submission.
