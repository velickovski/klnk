# Two-account internal walkthrough

Run `npm run dev` and `npm run mobile:web` in separate terminals. Open [iPhone browser preview](http://localhost:8081/?preview=iphone). **Call klnk** is the only opening action. After a voice attempt, Open workspace remains available even when microphone access fails. For direct typed inspection use [workspace](http://localhost:8081/?preview=iphone&workspace=1). This is Expo web, not a signed iPhone artifact.

1. In one browser context create fictional Alice; in another independent browser/private context create fictional Jordan Lee. Choose account sign-in instead of the earlier telephone simulation. Registering creates a member identity without a telephone number. Existing browser sign-in is memory-only: sign back into the same registered account after reload; do not create another demo account to recover an identity.
2. In Jordan's **People**, read Jordan's opaque member code. Alice enters that code in **People** to create an internal invitation. Nothing is sent by email, SMS or a third-party provider. Jordan accepts it in klnk. Both inspect their immutable account IDs and directional inbound permission. Similar display names do not establish identity.
3. Each owner opens **Settings**, selects a delegation preset, explicitly chooses the accepted member and topics (for example `launch`), working hours, IANA timezone, duration, notice/window and expiry. Review the preview, acknowledge authority and save. Default autonomy is off. Jordan can allow routine acceptance, or retain an owner decision for every meeting.
4. Alice says on browser voice home or types in Inbox: “Arrange thirty minutes with Jordan Lee next week after 2 pm to discuss the launch.” Natural-language planning needs the server-held OpenAI key; exact `Tell Jordan Lee that ...` information can use its faithful local path. A permitted routine model meeting proceeds under current autonomy; other prepared text is an exact inspectable draft before confirmation. Missing/ambiguous members, unavailable planning or uncertain results stay explicit.
5. The structured typed **New internal request** form is also available in Inbox. Choose an accepted connection, meeting, topic, purpose, one to three explicit offset/UTC intervals and IANA timezone. This form needs no model. Submitting a message has no meeting authority. Supplied local clock times without an offset are rejected; repeated DST times require clarification in natural-language planning.
6. Jordan may close the client. The running server worker checks both independent grants and the internal calendars. Within matching authority it commits one event and each owner's reminders. Outside routine timing, only the affected recipient receives an exact-proposal decision. Pending approval never means consent. A changed policy, block, deadline, conflict or cancellation stops/reconciles the task.
7. Jordan signs into the same account and opens Inbox. Inspect the factual summary, shared exchange and exact agreement. Attribution distinguishes an agent accepting under a rule from Jordan personally approving. Marking read changes only a read receipt. Calendar shows the same shared event and Jordan's own reminders. In-app notices are available on return; no APNs/local-notification delivery is promised.
8. Cancel with the event's current revision to update the shared record, both summaries/reminders and outbox atomically. A material change requires a new request and fresh matching acceptances. No unilateral rescheduling is hidden inside an edit.

For voice, save the separate **three internal voice permissions** in subsequent Settings, then start a new browser voice conversation. Changing credentials or rules is not an implicit grant. Existing Live cleanup/recovery still blocks another paid start until prior closure is confirmed. Native continuous Live remains explicitly unsupported until a compatible transport and physical-device evidence exist.

Privacy: Memory starts private and unconfirmed. An answer can disclose only confirmed, unexpired, explicitly shared facts selected in the recipient's current policy for that member/topic. Other private rules and schedules never become a shared agent transcript. Retention applies the shorter owner's 7/30/90-day setting to terminal shared content after a past event ends; future meetings/pending decisions are preserved. The worker sweeps hourly. A non-content retry tombstone remains. Cached source/plan text for a removed shared request is scrubbed too, including during peer deletion and backup reconciliation; old command reads/replays return410. Own private memories, policies and commands that never became shared records remain until owner/account deletion; expiry removes permission to use a fact rather than pretending it was erased from every backup.

Account export includes only the account's private network records and permitted shared records. Account deletion removes shared content for both participants and related reminders; a backup restore requires the independent deletion journal. Deletion cannot make already-read information disappear from another person's memory. OpenAI processing/contractual retention is separate from klnk record retention.

The [QA report](reports/qa.md) states which steps were executed with fictional accounts and which native/manual checks remain unrun. No real person's account or external service is needed for the deterministic walkthrough.
