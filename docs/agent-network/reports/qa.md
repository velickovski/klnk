## Independently exercised behavior

The API cases reject injected principals, unconnected callers, stale connection revisions and unknown request nonces. Two simultaneous exact requests return one identity; a changed payload with the same nonce conflicts. An incoming instruction to ignore rules remains an information message and cannot create a meeting or disclose a memory. Both acceptances must reference the exact proposal hash/version, with distinct authenticated owners; reading never approves it. An exception outside routine bounds requires only the relevant recipient's own explicit approval, while topic and capability denials continue to apply.

Queued work rereads revocation, block, denied inbound permission and mute before producing shared exchanges. Questions disclose only memories simultaneously selected by policy, confirmed, owner-entered, unexpired, correctly topic scoped and explicitly member scoped. Private, expired, unconfirmed, wrong-member, wrong-topic and unselected sentinel facts are absent. Foreign memory mutation, shared-conversation access, reminder dismissal, event cancellation and notification read are rejected. Account exports contain the requesting owner's policy and exclude peer private memories.

No answer and conflicting candidate times produce unresolved summaries. Pending decisions expire, queued cancellation prevents effects, calendar cancellation uses the shared revision and updates both owners' reminders and conversation. Preferences validate allowed retention values, reject actor fields, check revisions and remain private to the owner. Quiet notification mode preserves canonical Inbox results. Retention uses the shorter participant preference, preserves future meetings until event end plus retention, removes the event/reminder/outbox closure, and leaves a content-free nonce tombstone that returns 410 for stale replay.

Real PostgreSQL cases cover competing workers for the same request; overlapping requests on the same connection; overlapping requests across different connections sharing one owner; process death after event/reminder/outbox writes but before transaction commit; successful restart without duplicated effects; policy revocation committed while a worker waits for owner locks; cancellation after rollback; participant deletion after rollback; and real authenticated API calls whose bearer is revoked or expires during an owner-lock wait. The latter return `401 session_expired` with zero conversation writes. These cases use actual database row locks, not a JavaScript mutex.
